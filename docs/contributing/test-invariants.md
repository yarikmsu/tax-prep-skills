# Test-suite invariants

What each block of the test suite pins down, and which load-bearing rule
would break if an assertion were weakened. Relocated verbatim from CLAUDE.md.
Per-PR implementation history lives in `docs/changelog/`.

## The suite
- Test suite: `source .venv/bin/activate && python3 -m pytest tests/ -v`
- 2928 passed, 2 skipped (2930 collected) covering all computation functions, with hand-computed expected values from IRS worksheets, + FL type-none state module (template/freshness, sales-tax input, harvest banner, capability note, property calendar, registrations). **Per-PR / per-Codex-round implementation history lives in `docs/changelog/` (one file per epic I–P + `pre-epic.md`); the load-bearing invariants each block must preserve are inventoried below.** When adding a test, update the count above; when changing an assertion, update its worksheet comment. When two branches both bump it, do not add the deltas — run the suite on the merged tree and use what it prints.
  - **An artifact digest is not PII, and the bare-SSN rule cannot tell them apart (`test_pii_content_scan.py`):** a sha256 is 64 hex characters, and a maximal run of EXACTLY nine digits occurs inside one often enough that `requirements.txt` tripped the content scan 52 times the first time the tree was pinned with `--generate-hashes`. The scan's documented escape is `--no-verify`, so a gate firing on correct data every time the lock is regenerated would train contributors to bypass the PII scan itself — the exact failure this repo has already paid for. `strip_artifact_digests` removes the digest TOKENS before counting, scoped along BOTH axes so it can never become a hiding place: the exact PATH (`requirements.txt`/`requirements.in`, never a name pattern or a directory) and a token that must be the literal `--hash=sha256:` plus exactly 64 lowercase hex characters. Three tests hold that line — the lock passes, a real SSN on a comment line in that SAME file still blocks, and the identical digest line in `notes.md` still blocks, because keying on token shape alone would let any secret be laundered by prefixing it. The false-positive test is mutation-verified to fail without the exemption; the two blocking tests pass either way by design, since their job is to prove the fix did not widen.
  - **`A...B` excludes A, and for one base that is a hole rather than an optimization (`test_pii_content_scan.py`):** range mode resolves a merge base and enumerates `merge_base..head`, which omits the base commit — correct for CI, where the base is already on `main` and was scanned by the pull request that landed it. A ROOT commit is the single base for which that justification is false: nothing precedes it, so no earlier range can ever have covered it. The consequence was not theoretical — the full-history audit that gates publishing a private repository is `$(git rev-list --max-parents=0 HEAD)...HEAD`, and it reported `PII scan clean — 1 commit(s) inspected` over a root commit holding a full SSN. The per-commit loop already handles a parentless commit (it diffs against the empty tree), so the fix is to append the base to the revision list when `<base>^` does not resolve, and nothing else. Two tests, deliberately paired: the root base BLOCKS and names the file, and a non-root base is still EXCLUDED — without the second, widening `A...B` to always include its base would pass the first while failing every PR for content that already passed its own review. The first is mutation-verified to fail without the fix; the second passes either way by design, since its job is to prove the fix did not widen. The coverage-line test was rewritten to start from a non-root base for the same reason: it had been silently exercising the broken path, and its file count moved when the hole closed.
  - **600 on the files, 755 on the directory holding them (`test_archive.py`, `test_scenario.py`, `test_tie_out.py`):** AGENTS.md §1 requires `chmod 700` on the runtime directories precisely because a 600 file still sits inside a world-readable LISTING, and under `archive/` the listing is the disclosure — `documents/W2_Acme.pdf` names an employer before anyone opens it. Three `agents/lib/` sites created directories with a bare `mkdir` and then chmod'd only the files: `archive.py` (`archive/`, `archive/{year}/`, and the subtrees it moves in, which arrive carrying their root mode), `scenario.py` (`scenarios/`, whose FILENAMES are the scenario names), `tie_out.py` (`summaries/`, one file per source document, named after it). Every one landed at 0755 under a normal umask while the public `SECURITY.md` promised 0700. **Each test pins umask 022 for the duration**, without which the assertion is vacuous: `mkdir` asks for 0777 and umask 077 subtracts its way to 0700 unaided, so the test would pass against the unfixed code on a hardened developer machine and fail nowhere. All three are mutation-verified red before the fix. `mkdir(mode=0o700)` is not sufficient on its own and the chmod is not redundant with it — `mode` reaches the leaf only (Python creates `parents=True` levels at the default), and is ignored outright for a directory that already exists, which is the ordinary case for `scenarios/` and `summaries/`. The failure semantics match across all three sites, each raising its own error type on a chmod `OSError` rather than swallowing it: `archive.py` raises inside the try, so it rolls back and surfaces as `ArchiveError` with no half-created archive — a directory whose mode could not be set is one documents do not get moved into — and `scenario.py`/`tie_out.py` raise `ScenarioError`/`TieOutError` and remove whatever was written rather than leaving it at an insecure mode. `tie_out.py` runs inside the tie-out HARD GATE, but that is an argument FOR failing closed here, not against it: a filesystem quirk that silently left a report unsecured would be a worse outcome than a blocked return the gate already exists to produce. `test_atomicity_rollback_on_chmod_failure` was rewritten in the same change: it injected on chmod CALL #1, which is now a pre-move directory chmod, so it would have exercised the nothing-was-moved path and passed while proving nothing about rollback — it now targets the first chmod on a FILE and asserts it actually fired. What the tests did NOT cover was the larger half: the directories created by the AGENT rather than the library. That half is now covered by skill instructions instead of library code, and by `test_secure_fs.py`'s two skill guards rather than a filesystem assertion — `/tax-setup` creates and secures `documents/` and `summaries/`, and `tax-review`/`tax-project`/`tax-withholding` do the same for theirs. Only the WORKSPACE ROOT is still manual, because nothing in the toolkit creates it; `SECURITY.md` names that one boundary rather than claiming the mode outright.
  - **`os.replace` carries a file's mode across the rename — write-then-chmod on a `.tmp` predecessor does not guarantee the same thing (`test_rollover.py`):** `apply_changes` wrote `tmp_profile`/`tmp_result` via `Path.write_text`, which creates a NEW file at the shell's default mode (typically 644 under umask 022), then handed it to `os.replace`, which renames the file's content AND mode onto the real target — so the trailing `os.chmod(..., 0o600)` only tightened `taxpayer_profile.json`/`result.json` after the rename had already landed them at 644, and the restore path on a failed second replace (`targets.profile.write_bytes(original_profile)`) writes into the file at whatever mode the first replace left it, never tightening it at all. Fixed the way `scenario.py`/`tie_out.py` already were: create the `.tmp` file at 600 via `os.open` before any content is written, `fchmod`-ing the open descriptor (falling back to a path chmod where `os.fchmod` is unavailable, i.e. Windows) rather than trusting `mode=` alone, since POSIX ignores that argument when a `.tmp` path is left behind by a prior failed apply. `test_apply_changes_tmp_file_is_600_before_replace` spies on `os.replace` and asserts the SOURCE path's mode at the moment of the call — the only point in the sequence where the pre-fix bug is directly observable, since the trailing `os.chmod` on the final target passes either way.
  - **`os.chmod`/`Path.chmod` are POSIX-only enforcement wearing a cross-platform name (`test_secure_fs.py`, `test_scenario.py`, `test_tie_out.py`):** every `chmod 600`/`chmod 700` call site across `archive.py`, `rollover.py`, `scenario.py`, `tie_out.py` and `tax_calendar.py` was silently non-enforcing on Windows despite AGENTS.md §1 requiring owner-only access to every PII/financial runtime file and directory it names — `os.fchmod` does not exist there at all, and `Path.chmod()` only toggles the read-only DOS attribute, touching nothing about which other local accounts can read or list the file. `agents/lib/secure_fs.py` centralizes every one of those call sites behind `secure_path()`/`secure_fd()`: `os.chmod`/`os.fchmod` on POSIX (unchanged behavior), and on Windows PowerShell's `Get-Acl`/`Set-Acl` building a *protected* DACL — `SetAccessRuleProtection($true, $false)` blocks inheritance without copying the inherited rules down as explicit ones, then every remaining explicit rule is removed via `RemoveAccessRule` before the one new rule (the current user, Full Control, resolved from `WindowsIdentity.GetCurrent()` rather than a spoofable `%USERNAME%` string) is added. An `icacls /inheritance:r /grant:r` one-liner was tried first and REJECTED on review: `/grant:r` only replaces grants for the ONE user named, leaving every OTHER principal's existing explicit ACE (a prior owner, a share-level "Everyone" grant, anything left over from a move out of a shared location) untouched — a path could pass that command and still be readable by another account, exactly the gap AGENTS.md §1 exists to close. A failing PowerShell invocation, or the subprocess call itself erroring or timing out, raises `OSError` rather than silently leaving the file at its prior ACL; `test_secure_fs.py` covers all three with `os.name` monkeypatched to `"nt"` and `subprocess.run` stubbed, since real NTFS ACL enforcement can't be exercised from this project's POSIX-only CI — the stubbed assertions check the *script text* for the protect/clear/add sequence and the resolved-identity call, not a live ACL. The refactor moved the actual `os.chmod`/`os.fchmod` call out of `scenario.py`/`tie_out.py` into `secure_fs.py`, which broke two chmod-failure tests in each of those files that monkeypatched `Path.chmod` directly — a class-method patch, unlike `os.chmod`, which is a singleton module attribute reachable (and therefore patchable) through ANY importer's `os` name, which is why the `archive.py`/`rollover.py` chmod-failure tests kept passing unmodified through the same refactor. All four rewritten tests now patch `<module>.os.chmod` instead, matching the technique `test_archive.py`'s own chmod- and scandir-failure tests already used.
  - **A junction is a reparse point `Path.is_symlink()` cannot see (`test_secure_fs.py`, `test_archive.py`, `test_tie_out.py`):** an NTFS junction carries a different reparse tag (`IO_REPARSE_TAG_MOUNT_POINT`) than a symlink (`IO_REPARSE_TAG_SYMLINK`) and — unlike a symlink on older Windows — needs no elevated privilege to create, so `Path.is_symlink()`/`os.path.islink()` return `False` for one. Every symlink-refusal check this codebase already had (`archive.py`'s `_refuse_symlink`/`_refuse_symlink_destination`, `tie_out.py`'s inline `summaries.is_symlink()` guard) existed specifically to stop a runtime path from silently resolving outside the workspace, and a junction defeated every one of them on Windows: `archive/` junctioned to an external directory would pass straight through to `mkdir`/`secure_path`, which would then harden that external target and move a taxpayer's files into it. `secure_fs.is_reparse_point()` takes ONE `os.lstat()`, answers the symlink question from `stat.S_ISLNK(st.st_mode)`, and then — only when `os.name == "nt"` — reads `st.st_file_attributes & stat.FILE_ATTRIBUTE_REPARSE_POINT`, catching a junction alongside a symlink. That attribute is the GATE, not the answer — see the reparse-TAG bullet below. (An earlier version of this note described it as calling `Path.is_symlink()` first; it does not, and the reason is the fail-closed bullet below.) `archive.py`, `tie_out.py`, `parse_utils.py` and `tax_law_fetcher.py` all call it everywhere they previously called `is_symlink()` directly. `test_secure_fs.py` simulates a junction (real ones can't be created on POSIX) by wrapping `os.lstat`'s real return value with the reparse-point attribute added, careful to keep the real `st_mode` intact — `S_ISLNK` is consulted before the attribute and needs a working `st_mode` to answer correctly, and monkeypatching `os.lstat` (a singleton-module attribute, reachable through any importer's `os` name) affects that call too. A second fix rode along in the same function: `is_reparse_point()` used to re-wrap its argument in `Path(path)` unconditionally, and `pathlib.Path()` dispatches to `WindowsPath`/`PosixPath` based on `os.name` AT CONSTRUCTION TIME — so a test that monkeypatches `os.name` to `"nt"` to simulate Windows was, by that same patch, turning every `Path(...)` call in the process (including the one on an already-concrete `PosixPath` from a POSIX `tmp_path` fixture) into a `WindowsPath`, corrupting its own filesystem calls on the real POSIX runner. Fixed at the time by using an already-`Path` argument as-is rather than passing it back through the os.name-sensitive factory, and CLOSED later by dropping the wrap entirely — `os.lstat` accepts a string, so the conversion bought nothing and a plain string argument still went through the factory (see the Windows-spelling bullet below). `test_archive.py`/`test_tie_out.py` each add one junction-simulation test that patches `is_reparse_point` at the CALLING module's own imported name (`agents.lib.archive.is_reparse_point`, not `agents.lib.secure_fs.is_reparse_point`) — a `from X import Y` binding is a name lookup resolved once at import time into the importer's own namespace, unlike the `os`/`os.chmod` singleton-module pattern elsewhere in this codebase, so patching the source module's name would not be seen by a caller that already imported the function directly.
  - **`FILE_ATTRIBUTE_REPARSE_POINT` does not mean "this path redirects" (`test_secure_fs.py::TestOnlyARedirectingReparseTagIsRefused`):** Windows hangs a whole family of filter-driver features off that one bit — OneDrive Files On-Demand placeholders (`IO_REPARSE_TAG_CLOUD*`), Data Deduplication, the Windows Overlay Filter that compresses installed application files, container image layers — and every one of them is an ORDINARY file whose contents the filesystem produces on demand at the path you asked for. `secure_path`, `parse_utils` and `archive_year` all treat a reparse point as fatal, so the unconditional bit test refused normal taxpayer documents on any OneDrive-backed workspace: `/tax-parse`, `/tax-archive` and `/tax-setup` stopping with "symlink or junction" on a file that is neither. The refusal is keyed on the reparse TAG, and deliberately not on an allowlist of the two tags known to redirect — Windows marks every name-substituting tag with the documented `0x20000000` NAME SURROGATE flag, so testing the flag also refuses redirecting tags added after this was written (WSL's `IO_REPARSE_TAG_LX_SYMLINK` is already one), with `IO_REPARSE_TAG_APPEXECLINK` named explicitly because it redirects without setting the flag. A reparse point whose tag reads 0 is REFUSED: `st_reparse_tag` is Windows-and-3.8+, so 0 means the attribute said "reparse point" and nothing could certify otherwise, which is an uninspected path rather than a benign one. Six tests, both directions, all mutation-verified against the bare-bit version: four redirecting tags refused, four benign tags treated as ordinary files, the unreadable tag failing closed, the tag ignored when the attribute is unset, and — the reported symptom end to end — `secure_path` applying its ACL to a cloud-backed `W2_Acme.pdf` while still raising `PathRefused` on a junction. The `stat` module exposes `IO_REPARSE_TAG_*` only on Windows (`Modules/_stat.c` guards them with `MS_WINDOWS`), so both the module and the tests spell the values out; that is also what lets the branch run on the POSIX CI box at all.
  - **A shallow clone's boundary commit is indistinguishable from a root commit by traversal (`test_pii_content_scan.py`):** `git rev-list --parents -n 1` and `git rev-parse <sha>^` both report the parents THIS CLONE HAS, and in a shallow clone the boundary's parents were never fetched — so both describe it exactly as they describe a true root. Read as a root, the base is appended to the scan set and later diffed against the empty tree: its entire SNAPSHOT is scanned as newly-added content, including files carried down from history the range never asked about, and a pull request fails on content some earlier reviewed commit legitimately holds. The commit OBJECT always carries the true parent list — a graft only hides it from traversal — so `read_recorded_first_parent` reads it, and only the HEADER block, every line before the first genuinely empty one. That last part is the invariant `git cat-file -p | grep '^parent '` broke: it false-matches a commit MESSAGE line beginning "parent " (the pinned case is "parent bug tracked separately"), which reads as "this commit has a parent", excludes the base, and silently reopens the initial-import bypass the root special case exists to close. Inside the range the answer is the opposite: a commit recording a parent this clone does not have cannot be diffed against it, and the old `git rev-parse <sha>^ || echo $EMPTY_TREE` widened that silently into a whole-snapshot scan reported afterwards as "N commit(s) inspected" — coverage the scan did not have — so it now BLOCKS and names the fix (`fetch-depth: 0`). Written in pure bash rather than `grep`/`awk` for the reason the rest of the gate is: a `grep` that cannot RUN reports "no match", and no rule here may be turned off by a failure to test it. Three tests, each mutation-verified: the boundary base passing on a clean range, the root-with-"parent"-in-its-message base still blocking, and the missing recorded parent blocking rather than reporting a verdict.
  - **Skill instructions had the identical Windows chmod gap `secure_fs.py` was built to close, one layer up (`test_portability.py::test_every_bash_block_in_every_skill_parses`):** `tax-setup/SKILL.md`'s `summaries/` directory and `tax-parse/SKILL.md`'s per-document summary files (Step 3's per-file call and Step 6's backstop sweep) were hardened in an earlier round with a bare shell `chmod 700`/`chmod 600` — correct on POSIX, but under a Windows POSIX-compatible shell (WSL/Git Bash) that `chmod` binary hits the exact same DOS-attribute-only gap `os.chmod` had, bypassing `secure_fs.py`'s enforcement entirely since the skill never calls into it. That round missed three more sites in the SAME two skills that a later review caught: `tax-setup`'s `taxpayer_profile.json` chmod (Step 3) and `result.json`/`answers.md` chmod (Step 5), and `tax-parse`'s `parse_ledger.json` chmod (Step 6.5) — a documentation claim in `agents-compat.md` had asserted the migration was complete for "any `SKILL.md` step" while these three still ran a bare `chmod`. All now invoke that CLI instead (written `python3 -m agents.lib.secure_fs` at the time; every call site later moved behind `sh agents/lib/run.sh`) — a CLI the module exposes for exactly this, secured-per-path with the same `secure_path()` used everywhere else, silent on success and printing `Could not secure {path}: {error}` to stderr with a non-zero exit on any failure. `test_cli_secures_each_given_path`/`test_cli_exits_nonzero_and_reports_failure` in `test_secure_fs.py` drive it as a real subprocess (`python3 -m agents.lib.secure_fs`), the only way to exercise an `if __name__ == "__main__":` argv branch without executing the rest of the module's file-scoped code under a borrowed `__name__`. The module's `if __name__ == "__main__":` block now branches on argv: no arguments runs the existing self-test (unchanged), one or more runs the CLI — the same split `archive.py`'s own argv-driven CLI block already uses, so a bare `python3 agents/lib/secure_fs.py` (AGENTS.md §7's "every module self-tests when run directly") is unaffected. That round scoped `agents-compat.md`'s claim to `tax-setup`/`tax-parse` and named every other skill as a known gap; the round after it closed the gap and re-widened the claim — but re-widened it one skill too far. `tax-amend` still ran `chmod -R 600` over `archive/{year}/as_filed/` (a full copy of `result.json`, `taxpayer_profile.json`, `answers.md` and `summaries/`), and `tax-compute` had NO securing step at all, because it writes `result.json` and `answers.md` from `references/finalize.md` and the guard globbed `tax-*/SKILL.md` only. Both are fixed and both guards now read `SKILL.md` PLUS `references/*.md`: **a skill is a directory, and a check that reads only its body scores the progressive-disclosure files as green by not looking at them.**
  - **`is_reparse_point()`'s own inspection failure was the one path left fail-OPEN in an otherwise fail-closed module (`test_secure_fs.py`):** the Windows branch caught every `OSError` from `os.lstat()` — including a transient I/O error or an access-denied result from a misbehaving junction target — and returned `False`, certifying an uninspected path as "not a reparse point." A caller's `exists()`/`mkdir()` follows the same link the failed `lstat` couldn't read, so the one case most likely to indicate something IS wrong with the path was exactly the case treated as "nothing is wrong." Narrowed the except clause to `FileNotFoundError` only — the sole case where "not a reparse point" is actually correct, since a path that doesn't exist can't be one — and let every other `OSError` propagate. **The first version of this note claimed "both `archive.py` and `tie_out.py` already wrap their reparse checks in a broad `except Exception`", and that was false for exactly the three sites where it mattered**: `archive.py`'s two destination-component checks and its whole dry-run loop sit ABOVE `archive_year`'s `try`, and `tie_out.py`'s `summaries/` check sits in `write_report` outside any try — so the newly-propagating `OSError` escaped as a bare traceback past the `except ArchiveError` in `__main__` (the handler that prints the `ERROR: …` line the skill tells the agent to read) and past `_main`'s `except TieOutError`. Fixed by translating at the ONE place each module's checks route through: `archive.py` gained `_is_reparse_point_or_raise()` (and the three redundant `if is_reparse_point(src): _refuse_symlink(src)` guards collapsed to a bare `_refuse_symlink(src)`, which re-evaluates the same predicate internally — the outer `if` was a second `lstat` per entry buying nothing), and `write_report` wraps its own call. `test_is_reparse_point_false_on_windows_file_not_found` pins the narrowed case; `test_is_reparse_point_fails_closed_on_other_windows_lstat_errors` is mutation-verified red against the pre-fix code (an unqualified `except OSError: return False` swallows the `PermissionError` the test raises instead of letting it propagate); `test_uninspectable_destination_raises_archive_error_not_a_bare_oserror`, its dry-run sibling, and `test_write_report_translates_an_uninspectable_summaries_path` pin the translation at all three previously-uncovered sites.
  - **A permissions fault must not be able to mask a tax-correctness fault (`test_tie_out.py`):** `write_report` was called INSIDE `_main`'s main `try`, so once it was hardened to fail closed on a chmod/write error, any such error jumped to `except (TieOutError, RolloverError): return 1` — before the verdict was printed and before `2 if report.failed else 0` was ever evaluated. A return with a dropped 1099 (the CP2000 case the whole gate exists for) would therefore report exit **1** on an unrelated NFS/ACL hiccup, which `tax-compute` Step 12.7 documents as "`parse_ledger.json` is missing or malformed" — sending the agent to fix a ledger that is fine — and neither the markdown nor the `--json` block would be printed at all, so the failure was not merely mislabelled but invisible. The report is fully computed by that point, so the fix is ordering: print the verdict, fix `exit_code = 2 if report.failed else 0`, THEN persist, and on a write failure return `max(exit_code, 1)` — never below 1 (the write really did fail, so it is not a clean pass) and never below the verdict's own code. `test_main_failing_gate_exits_2_even_when_the_report_cannot_be_written` and `test_main_passing_gate_exits_1_when_the_report_cannot_be_written` are both mutation-verified red against the pre-fix ordering, and the failure output is the bug verbatim: `out=''` with exit 1 where 2 was owed.
  - **A protected DACL with a non-inheritable ACE is owner-only for the directory and for nothing inside it (`test_secure_fs.py`):** `_secure_path_windows` built its single `FileSystemAccessRule` with the 3-argument constructor, which means `InheritanceFlags.None`. On a directory that breaks both directions at once. Downward: `SetAccessRuleProtection` + `Set-Acl` propagates the inheritance change to existing children, so a `summaries/*.md` whose only ACEs were inherited from `summaries/` is left with an EMPTY DACL — the owner locked out of their own parse summaries, breaking `/tax-review` and `/tax-generate`. Forward: anything created inside afterwards inherits nothing and falls back to the creating token's default DACL, which normally grants SYSTEM and Administrators — where POSIX `0700` denies traversal and therefore covers every child for free. The script now branches on `$item.PSIsContainer` and gives a directory `'ContainerInherit,ObjectInherit', 'None', 'Allow'`, keeping the 3-argument form for a leaf (inheritance flags on a file are invalid and throw). `test_secure_path_windows_directory_ace_is_inheritable` asserts the branch and the flags in the built script text — the same POSIX-CI boundary every other Windows assertion in this file accepts.
  - **`secure_path()` itself refuses a reparse point, because the skill layer's own guard cannot (`test_secure_fs.py`):** `/tax-setup` Step 1 guards `summaries/` with the shell test `[ -L summaries ]`, which is POSIX-only — it is FALSE for an NTFS junction, the exact case `is_reparse_point()` was added for — and `mkdir -p` treats a junction to a directory as already satisfied. Since `secure_path()` performed no reparse check of its own, a junctioned `summaries/` would have had the protected DACL applied to whatever it pointed at, and `/tax-parse` would then have written the taxpayer's parsed W-2 summaries outside the workspace, past every gitignore and PII rule scoped to it. `secure_path()` now refuses one itself, so the guarantee holds at the layer every caller — library and skill CLI alike — passes through, rather than depending on a POSIX-only test written in prose. `test_secure_path_refuses_a_symlink` also asserts the external target's mode is UNCHANGED (the refusal is what matters, not just the raise), and `test_cli_refuses_a_symlinked_path` drives it through the real subprocess so the non-zero exit `/tax-setup`'s block treats as a refusal is covered end to end.
  - **A preview that skips the subtrees the real run refuses is worse than no preview (`test_archive.py`):** `archive_year`'s `dry_run` branch inspected only the ten top-level entries, while the real run also walks each moved subtree refusing any nested symlink/junction — so a `documents/cloud_sync` symlink produced a preview reading "will move documents/", which the user confirms, and the real run then raises *after* five files have already moved and been rolled back. The dry run now walks the same subtrees with the same `onerror=_raise_walk_error`, and translates the re-raised `OSError` into `ArchiveError` — that loop sits outside the real run's `try`, the identical exposure the reparse checks had. Three tests: the nested refusal now fires in dry run (mutation-verified red), an ordinary nested directory still previews clean (so the walk cannot have been made to refuse everything), and an unreadable nested directory raises `ArchiveError` rather than a bare `PermissionError` — without which `os.walk`'s default swallow would return a silently partial preview reading as clean.
  - **`os.fdopen` adopts a descriptor only on success (`agents/lib/{scenario,tie_out,rollover,tax_calendar}.py`):** all four write paths do `fd = os.open(..., 0o600)` then `with os.fdopen(fd, ...)`. If `os.fdopen` itself raises — `MemoryError` building the buffered wrapper, an `OSError` from the seekable/isatty probe on an exotic filesystem — it has not taken ownership, the `with` never runs, and no `except` closes the raw descriptor: `scenario.py` unlinks the path and raises `ScenarioError` while leaking the fd. A long-lived agent session that repeatedly re-saves scenarios or re-runs the tie-out gate against a failing filesystem walks to `EMFILE`, after which every later `os.open` in the process fails — including the ones writing `result.json`. All four now wrap the `fdopen` call and `os.close(fd)` before re-raising; `rollover.py` opens two descriptors per call, so it compounds twice as fast. The refusal is scoped by a PARTITION of the lock (`_PARSING_TREE` / `_GENERATION_TREE`) pinned by `test_every_locked_distribution_is_classified`: refusing to read a 1099 because the PDF *generator* was upgraded is the cry-wolf shape, and a new transitive package landing in neither set — what an ordinary bump produces — would silently escape the check. `extract_csv` is deliberately outside it (stdlib `csv`, no locked package, and /tax-parse-crypto runs on exchange CSVs), an unreadable lock refuses rather than passing as verified, and one test asserts the real workspace refuses NOTHING, since a refusal that fires on a correct tree is the same defect one bit over. The fifth entry point is the one most easily missed and the only one where placement is load-bearing: `scan documents/` is the FIRST command /tax-parse runs, it opens every PDF to classify it, and its output is the routing table for everything after — inside a `try` that turns any exception into a `doc_type: "error"` entry and a stderr line, so a refusal placed one line lower degrades into a warning and the scan returns a list built by the parser it was refusing. It sits OUTSIDE that handler and PER-PDF, both pinned by their own test, since hoisting it to the top of the scan refuses a CSV-only workspace that opens no locked parser at all. **A tenth pass made that comparison pick the RIGHT pin.** The versions for one name were pooled into a set and an installed version accepted if it matched any of them, which is correct only while a name is pinned once. A `--universal` lock pins one name TWICE under opposite markers (`python_version < '3.12'` and `>=`) at two different versions, and the pool then accepts the version meant for the other interpreter as locked — so the parse boundary reads the tree as pinned and opens a taxpayer's documents on a stack the suite never ran there. Each version is now kept PAIRED with its own line's marker verdict, and `_pins_here` splits a name's pins into the ones that apply here and the ones whose marker could not be read; a definitely EXCLUDED pin is in neither, so it is neither required nor compared against — PyPy ships its own `cffi`, and `pip install -r requirements.txt` will neither install nor remove it. Three states fall out, and each is a channel rather than a guess: installed-and-not-the-applicable-version is drift, reported against the applicable pin ALONE, since a record naming both lines tells a reader on this interpreter to install the one meant for the other; installed under an unreadable marker at a version no readable pin names goes to the undecided channel, answering it either way being an alarm the remedy cannot clear or a certification of an unexamined pin; and a lock naming two versions that BOTH apply is reported as undecidable rather than resolved by picking one — the pooled-set fail-open surviving in the single case where the pool is genuinely ambiguous. The twice-pinned test now derives its markers from the running interpreter's own minor: written against a fixed 3.12 it asserted the opposite of what it says on 3.10 and 3.11, both of which `MIN_PYTHON` admits.
